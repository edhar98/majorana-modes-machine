What We Learned From Using LLMs

A review of an AI-heavy seminar workflow: what helped, what failed, what made the project reproducible, and what we would recommend to students using LLMs for research-style work.

Overall experience

We learned a lot. The project grew far beyond a normal 5 CP seminar task, precisely because LLMs made it cheap to keep expanding scope: physics derivations, code, plots, slides, notes, audits, and finally this web page.

The paid coding assistants were clearly stronger for sustained work. We mainly used Claude (Opus 4.8) and ChatGPT (GPT‑5.5) inside Cursor, and tried NotebookLM, Gemini, and DeepSeek early on. NotebookLM was good for concept understanding and visual learning, but weaker for continuous, file-based project work.

Final takeaway

LLMs can multiply your productivity — but only if the project is organized enough that both you and the agent can verify what is true.

Workflow that worked

Start with the environment

Before any physics, set up the workspace: a clear project structure, Git/GitHub, reproducible commands, and a shared instruction file. Here AGENTS.md became the agent's persistent memory and kept style, conventions, and build commands stable across weeks.

Everything is a file

A Linux, file-first workflow was decisive: code, LaTeX, notes, prompts, build scripts, and caches all became files you can version, diff, and verify. That is also how you control an agent's memory — and why we preferred CLI and file-based tools over web chat, where knowledge stays trapped in the window.

Short, focused agents

For hard tasks, a fresh agent with clean context beat overloading one long conversation. Knowledge-style side questions belong in a separate thread or an aside command, so the main task — plotting, coding, a deck — does not drift.

Advisor and audit patterns

Complex steps benefited from a main agent consulting advisor agents, running subagents in parallel, and cross-model review. We even had Opus 4.8 write the prompt for a Fable 5 audit of the whole project.

Project highlights

From physics to infrastructure

The most valuable output was not text but reusable infrastructure: block runners, Makefile targets, LaTeX notes, slides, dependency checks, and this GitHub Pages build.

Build tools, not repeated commands

Know when to play ignorant and when to be specific. If you cannot compile LaTeX you can ask the model every time — and stay dependent. If you know the command, ask it to write a Makefile target both human and agent reuse. The second path compounds.

LaTeX was a real advantage

LLMs are strong with text and cheaper in tokens on it. Writing notes and decks in LaTeX made everything easier to edit, review, compile, and keep consistent — and turned explanations into searchable project assets instead of lost chat windows.

Personal tips

The best results came from knowing when to be specific and when to let the model propose options.

  1. Read the generated code. Understanding it is what lets you write sharper prompts.
  2. Be specific when you already know the result; leave room for the model to be creative when you are genuinely exploring.
  3. Make the model cite exact files, commands, and outputs before you trust an “it's fixed.”
  4. Keep one canonical source of truth for the physics (shared runners), not scattered notebook-local copies that quietly diverge.

Risks and bad habits

Productivity can become laziness

Short prompts are efficient, but they erode writing discipline. The model tolerates rough text while the human slowly loses precision, grammar, and polish.

Learning can become too filtered

When most explanations come from an LLM window, awareness of cited, reviewed, trustworthy sources weakens. Scientific work still needs external references.

Confidence without proof

LLMs sound certain even when a sign convention, file path, dependency, or physics claim is wrong. Independent verification remains mandatory.

Generated artifacts need boundaries

Agents happily spawn extra plots, caches, thumbnails, and pages. That only helps when generated output is controlled and separated from source.

Future improvements

For a future seminar, we would make LLM use more collaborative, more reproducible, and more research-oriented from the start.

  • A shared team plan (for example Claude Team), provided by a professor or university, would give every student the same project context through persistent workspaces.
  • Topics could be more diverse and more research-oriented — ideally to the point where results become publishable.
  • Every plot should carry provenance: source script, command, parameters, cache inputs, and the slides or notes that depend on it.
  • Automatic checks should verify figures, notes, slides, caches, and web assets before publishing.
  • Review prompts should explicitly hunt for bugs, missing tests, invalid assumptions, and scientific weak points — while the student stays responsible for correctness, taste, and final judgment.
